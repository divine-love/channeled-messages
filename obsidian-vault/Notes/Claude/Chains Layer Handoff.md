## Where the chains layer lives

The two big files were split. Each kept its name as a small front-door file, and its bulk moved into a folder of the same name.

- `metadata/chains-log.md`: the log's design block and rules. It holds no entries.
- `metadata/chains-log/`: the entries, one file per year of message. The year is the first four characters of the message_id, so 2018-07-22-af-seretta-kem is logged in `chains-log/2018.md`. An entry file holds entries and nothing else: no front matter, no title. When a year grows too large to work in, it is divided by month (`2026-01.md`, `2026-02.md`) and its year file is removed; a year is kept whole or by month, never both. No script change is needed for that.
- `metadata/chains-threads.md`: the design notes, role vocabulary, registry, holding pen, patterns and open questions. It holds no rosters. Its `## Thread rosters` heading stays, because the roster files are read in at that point.
- `metadata/chains-threads/`: one roster per minted thread, in a file named for its slug (`soul-expiation.md`). The file opens with `### slug`, a blank line, then the entry, and holds nothing else. Minting a thread means adding its registry row and its roster file in the same commit. Renaming a thread means renaming its file.
- `.github/scripts/chains_io.py`: the helper that reads the front-door files and the folders, in name order, as one continuous text. The validator and the vault generator load it themselves; it is never run by hand. Because both read through it, they see the layer exactly as they did when each part was a single file.
- `last_updated` is carried by the two front-door files only. Change it when the front-door file itself changes (the rules, the registry, the holding pen, patterns or open questions). Entry files and roster files carry no date; the repository records when each changed.

## Starting a session

1. Work from the curator's committed files, never from memory or from project-knowledge search chunks, which can be stale. Pull the repo when it is attached and read the year files and roster files each message needs. Without the repo, ask for the two front-door files plus the year files and rosters in play. Diff any copy against the committed files before delivering changes. If the curator has not yet committed the last delivered files, build on those files, not on GitHub.
2. Run `python .github/scripts/validate_chains.py` (from anywhere in the repo) before and after every change. The ledger says what moved.
3. Anything the curator needs to see goes in the reply itself. Output printed inside a tool step is not visible to them.
4. Preserve line endings. In Python, open every chains file with `newline=''` on read and write. `Path.read_text` and `write_text` convert line endings silently and would rewrite every line of the file.
5. Commit text fixes and validator changes together, or the build fails on the gap between them.
6. When rewrapping roster prose, keep each section label (Foundation, Elaborations, Witnesses, Fences, What is awaited, Structural note and the rest) at the start of its own line. A line ending in a closing quote (`."`) is a sentence end too.
7. Anything in quotation marks in the log or a roster is the message's own words. Check every quote against the message text before delivering, and check again after any approved body-text edit: a log quote taken before an edit no longer matches the message once the edit is made (2016-12-08-af-augustine, "each and every one", was caught this way; 2017-04-20-af-augustine's "has been praying" and "No, my beloveds," were updated the same way).
8. Log lines start at column 0. A heading or NOTE line pasted with leading spaces breaks the build; check new entries for indentation before delivering.
9. Delivery, by the curator's decision of 2026-11-20: first set out every proposed change in the reply (the message fields, the text flags, the log entry and every roster or pen line, in full) and wait for her approval or changes. Nothing is packaged before she approves. Then send one zip holding every changed file at its repository path, built on her latest commit. The zip's top level is the repository's own folders (`content`, `metadata`, `spirits`, `.github` as needed), with no wrapping folder, and any review guide goes beside the zip, never inside it. She applies it from the repository's top folder with `Expand-Archive -Path "$HOME\Downloads\<name>.zip" -DestinationPath . -Force` (Windows, PowerShell). A zip that wrapped everything in a `channeled-messages/` folder once landed as a stray folder at the top of the repository instead of replacing the real files. Never push.
10. After the curator commits, check that each delivered paste landed as delivered. A roster paste once replaced the `divine-love-mediumship` witness line with Patterns text; it was found only by diffing every delivered roster change against the repo, and repaired with paste blocks.
11. `last_updated`, in the two front-door files, must be a zero-padded ISO date (`2026-11-01`, not `2026-11-1`). The validator fails the build otherwise.
12. In log and roster prose, write a file name as a path in parentheses, never in backticks: (content/practices/prayer-2017-05-20-af-jesus.md). The vault generator reads anything in backticks as a thread slug, so a backticked file name makes a stray thread page on the site. The generator now skips a backticked word that is not in the registry, but write paths anyway.
13. After every change, run `generate_vault.py` as well as the validators and check that it reports 0 quoted passages not located.

## Reviewing a message already in the archive

The curator often asks for the chains on a message that was catalogued before the current rules. Read it in full, propose the log entry and any roster changes, and bring the file up to the current rules in the same pass:

- em dashes removed from curator fields
- an excerpt that paraphrases or joins sentences replaced with an exact quote
- notes that assert beyond the text, or that report body-text corrections, trimmed (corrections go in chat)
- notes that call the message a first, an earliest or a latest trimmed (see No rank claims anywhere)
- a bare `gathering:` set to `""`, unless the message has a gathering
- the door ends with a full stop
- related lists sorted by date; links that share only a spirit, a setting or general encouragement dropped, since links are subject-specific only; links added where a message shares the subject closely
- message_type, primary subject, essential_teachings and missing Law subjects checked against their definitions
- a main category name used as a subject replaced with a subcategory

Body-text items still need the curator's approval. Give reciprocal blocks for every added link; a dropped link needs removing at the other end only if it was reciprocated.

## Standing rulings

These are the curator's rulings. Most are written into the design blocks of the two files. The reasoning is recorded here so it is not lost.

**The archive is mutable.** Messages arrive out of order, at both ends and in the middle, and role assignments stay provisional until a chain is built. So an entry states what its thread argues, never how much of it has been found, and the AI never interprets messages by quantity. In rosters and log records this rules out:

- counts of members, roles, messages, witnesses, spirits or instances
- spans of years
- rank claims (earliest, latest, fullest, clearest, strongest), including the hedged form "in hand", which is still a rank against a growing set
- claims about the whole set ("no other member carries this", "the thread lacks", "every other entry", "unusually for the thread", "so far", "otherwise only"); state the new facet positively, against a named message where a comparison helps
- claims that nothing is logged between two points
- intervals between messages ("three weeks earlier", "predates it by two years", "earlier in date than", "the next day"); the message_ids carry the dates
- intervals measured against a role ("three weeks before the Foundation"), since the role can move
- watches that wait on a count ("settle when a third message arrives", "look for a second instance"); write "a message that develops X" instead
- stale states ("the anchor is still awaited", "not yet logged", "anchors the new thread")

Instead, state the relation between named messages: one develops what another asserts, answers it, or repeats it without developing it. A count of passages inside one fixed message is fine, because a message's text does not change.

**No rank claims anywhere** (curator's ruling, 2026-11-20). The rank-claim rule above reaches beyond the chains layer to the whole repository: message notes, spirit and medium files, and every other curator-written text. Never call a message the first, the earliest or the latest, in the archive or "in hand". `schema.md` (Notes Field) says so; it used to tell curators to write "earliest in hand", and that wording is gone.

**Order of work.** Messages are not added in date order. The curator chooses each message, so any year may have gaps, and messages arrive at both ends of the archive and in the middle. Never describe the work as a "catch-up", call it sequential, or say where it "resumes". Check the index for a collision rather than assuming a message is new because of its date.

**Subjects are subcategory names only** (curator's ruling, 2026-11-20), so that every message is filed in its proper place. The main category names in `subjects.yml` group the subjects and are never used as a subject. If no subcategory fits, a new subject is proposed to the curator. `schema.md`, both schema files, the templates and `subjects.yml` say so. The subject census at the end of `validate_messages.py` shows, under "Top-level categories tagged directly", how often each main category name is still used. A guard that would fail the build if those uses rose was drafted and set aside by the curator.

**The log is the history of the messages, not the history of the log.** No mint dates, pen dates, session or reading dates, or curator attributions in records. Where a standing ruling governs a decision, name it descriptively ("the argument-not-image ruling"), never by the date it was made. A roster entry likewise explains its thread, never its own existence. Essential-teaching labels (Core Teaching, Spirit Biography and the rest) live in the message files, not in the log or the rosters.

**Full reading only.** Every log entry is made from a full reading of the message, never from its description or summary. The old `[back-search]` tag, for entries logged from a description, is retired: those entries proved unreliable (paraphrases and invented lines presented as quotes), all of them were read in full and rewritten, and the tag was removed from the log, the rosters' design block, the vault generator and the project instructions.

**Read with no thread.** Every message read in full for chains gets a log entry, by the curator's ruling of 2026-11-18. One that joins no thread has its heading line and the single record `- Read in full; joins no thread.`, word for word, and nothing else (for example, 2017-05-18-af-goldie, in `chains-log/2017.md`). It is the one record that speaks of the reading rather than the message, and the rule in `chains-log.md` says so. The validator rejects variant wording, the line beside thread records, and an entry with no records, and its opening line reports how many entries are read with no thread. The vault generator passes over the line. So the messages still to read for chains are exactly those with no entry.

**Voice.** Curator notes are impersonal: no "I", "my reading", or "JUDGMENT CALL". A question left for the builder reads "open question for build:". Recommendations addressed to the curator belong in Open questions in chains-threads, not in the log.

**Plain language.** All curatorial prose, including notes meant only for a builder, is written so anyone can understand it. Simpler wording, not dumbed down, and no jargon standing between the reader and the meaning. By the curator's ruling, chains language is to be very simple, "so simple, a child can understand it", because the thread pages are read on the public site. Say what the message says in everyday words: "she tells them everything they need to do", not "the requirement stated as a closed list"; "says it without explaining why", not "asserted rather than argued". The Conversation Prompt Kit carries the same line.

**Log order.** Entries are chronological by message date, and entries sharing a date go alphabetically by message_id (2016-12-10-af-andrew before 2016-12-10-af-james). Messages are not catalogued in date order, so a new entry is inserted at its position, not added at the end. One record per line; records are never wrapped. A message may carry more than one line for the same thread and role when each line covers a different passage; they count as one role, read in the order the lines give.

**Log headings** are `### message_id | title | date`, with the title exactly as in the message file. The medium is carried by the message_id and is not tagged in the heading. Whether a message is posted online is not tagged either; `canonical_url` in the message file records that. The format line in the `chains-log.md` design block now shows the pipes.

**NOTE vocabulary.** Five kinds are in use, and a sixth is retired:

- `(witness,` slug`)`, `(sighting,` slug`)`, `(considered and set aside,` slug`)`: grades the message as evidence for a thread. Working distinction: a witness states a step of the thread's argument without developing it; a sighting touches the thread's territory or wording without stating its argument. Notes for holding-pen candidates are sightings. The validator requires exactly one slug in the parentheses and nothing after it, so a role that was considered goes in the prose: `NOTE (considered and set aside,` slug`): considered as a Chrysalis. ...`
- `(build,` slug`)`: addressed to whoever builds that thread (a tension, a fence, a caveat about the text, an open anchor question, a pairing to read together)
- `(pattern, described and not penned)`: a recurring observation not yet a candidate thread, including the lattice of Light material
- `(context)`: retired by the curator's ruling of 2026-11-20, and never written in a new entry. The log holds only what develops threads. What a context note used to carry goes where it belongs: a fact about the message into its `notes`, a fact about a spirit or medium into that spirit or medium file, and nothing at all for a practice file, which already names its message. The `chains-log.md` design block, the project instructions and the Conversation Prompt Kit all say so. 73 older context notes remain in the log (23 of them point to prayer files) until the context-note audit (see Next). The validator still accepts the kind, so the audit retires it there once the old notes are gone.

A note touching several threads is split into one NOTE per thread. Notes made redundant by a later role line are kept as `build` notes, not deleted.

**Chrysalis.** The role is for a message that describes the transformed state itself, from within or as it stands, not one that forecasts what will follow a step. Elaboration had become the default for such passages, so whenever a message describes the transformed state, ask whether it is a Chrysalis and flag it to the curator rather than defaulting to Elaboration. A forecast is logged as considered and set aside (2016-12-10-af-james, "you will walk with a new stride", for `vanguards-of-change`). Chrysalis roles on file: `bell-toll-instrumentality`, `mind-vs-soul` (two lines), `soul-faculties`, `soul-expiation` (2018-07-14-af-seretta-kem, held as a candidate by the curator's ruling: it may give way to a message that describes the completed state more fully), and `two-paths` (2017-07-30-af-augustine, the soul the Divine road makes, "a being that reflects more the Divine than the human or the spirit", held as a presumptive anchor on the same terms).

**Ask about the special roles before Elaboration.** By the curator's observation of 2026-11-23, the log holds far more Elaboration lines than any other role (270 against 24 Objections removed and 6 Reframes when counted). Elaboration is right when a message adds a step, but before settling on it, ask whether the message names a belief and clears it (Objection removed), turns an idea around so it is seen differently (Reframe), describes the transformed state (Chrysalis), gives a first-hand account (Testimony), or completes the argument (Capstone). A review of the session's members on that day moved six lines: Reframes in `speaking-the-truth` (2017-07-22-af-seretta-kem, declare whose you are, not every plan) and `mind-vs-soul` (2017-07-22-af-seretta-kem, the lament as a sign of progress); Objections removed in `prayer-soul-longing` (2017-07-31-af-andrew, that sitting and waiting is enough), `simplicity-of-the-path` (2017-07-30-af-augustine, that the simple path cannot satisfy the mind) and `self-love-foundation` (2017-07-16-af-seretta-kem, that one is failing for not measuring up); and the `two-paths` Chrysalis above.

**Roster files.** Each roster is its own file in `metadata/chains-threads/`, named for its slug and opening with its `### slug` heading. The validator fails a file whose name is not its slug.

**Roster entries** follow the shape in the chains-threads design block: an opener naming the thread and its arc, then role sections in argument order (facet groups allowed within a section), then Witnesses, Fences, What is awaited, Structural note, in that order. Sightings stay in the log, except where one marks a thread's boundary. A message named in a roster as a member or witness should have a log entry that agrees with it. The registry is alphabetical, the roster files are read in alphabetical order by slug, and the holding pen is alphabetical. When a roster's single "Witness." gains a second message, the label becomes "Witnesses." A new role section goes after the role sections that come before it in argument order (an Objection-removed after the Elaborations, before the Witnesses).

**Prayer files.** Spirit-given prayers, including prayers a spirit offers for the circle and words a group is given to say together, get a practice file (`content/practices/prayer-{message_id}.md`, template in `content/templates/prayer-template.md`, checked by `validate_prayers.py`), and nothing else points to it: no log note and no line in the message's `notes`, because the practice file names its message (curator's ruling, 2026-11-20). Two kinds of words get no practice file: a declaration the seeker is given to affirm rather than a prayer addressed to God (2016-12-02-af-jesus, "I am a child of God"), and a prayer the circle already says that a spirit quotes rather than gives (2016-12-05-af-augustine, "Dear Father make me an instrument of your peace, a channel of your love"). Where one message gives several lines of the same prayer, one practice file holds them (2017-04-20-af-augustine). Prayer files show their title as a heading in the Obsidian vault, through `add_title_heading` in `generate_vault.py`.

**Questions in message files** never imply something the messages deny for the Divine Love path. For example, a question must not suggest that a soul far enough along that path could fall back into darkness.

**Posted or not.** `canonical_url` alone records whether a message is posted online: blank means no known public URL. The notes field does not carry "Not publicly posted online.", because messages are still being posted and the note goes stale.

**Titles** (curator's ruling, 2026-11-23). When a source has no title, the curator creates one, and a created title carries no mark: the asterisk once appended to such titles is retired. `schema.md`, `message.schema.yml`, `talk.schema.yml` and the message template say so, and the eight titles and log headings that carried one were cleared. `generate_vault.py` still strips a trailing asterisk when naming files, which is harmless.

**Gatherings.** By the curator's ruling, `gathering` holds the name of a retreat, an event or a named prayer circle, written exactly as the source gives it; never add a word such as "Retreat" to a name. It is blank (`""`) only for an unnamed home circle. "DLSF Board Meeting" is an accepted gathering. A venue, such as a church where a message was received, goes in notes, not in `gathering`. `schema.md`, `message.schema.yml`, `talk.schema.yml` and the message template say so. ## Quotes in context

By the curator's ruling, the published chain pages link to whole messages and never to a passage. This follows the design rule that the unit of linking is the whole message, so that a quote sends the reader to the full text and not to a line or two. The site is meant to be read in full, not mined for fragments.

The working mirror, Threads (working), is not published, and there each record carries an _In context_ fold-out: the paragraph each quoted passage comes from, with the quoted words highlighted. `generate_vault.py` works these out fresh from the message text on every build. Nothing is added to the message notes, so the published site is untouched. A quoted passage that cannot be found in the message, or in another message the record names, is listed at the foot of its fold-out, which makes the fold-outs a standing check on the quotes.

Paragraph links into the message notes were considered and set aside: they would need a hidden marker in every quoted paragraph of the public message pages, and would make it possible to link to a paragraph.

## The validator

`.github/scripts/validate_chains.py`, stdlib only, with its own workflow `.github/workflows/validate-chains.yml` triggered by changes to either front-door file, either folder, the script or `chains_io.py`. It reads the layer through `chains_io.py` and runs its checks on the joined text, so the checks are the same as before the split. Every message names the file and line to correct, as `chains-log/2018.md line 142`.

**Layout checks (any occurrence fails the build):** an entry in the wrong year's file; anything in an entry file that is not an entry; an entry file not named for a year or a year and month; a year kept both whole and by month; a roster file whose name is not its slug or that holds more than its one roster; an entry left in `chains-log.md` or a roster left in `chains-threads.md`; any file in either folder that is not a `.md` file.

**Hard checks (any occurrence fails the build):** both front-door files carry an ISO `last_updated`; the registry and rosters are alphabetical and every roster has a registry row; every slug in the log is in the registry or the holding pen; one record per line; entries chronological with no duplicate message_id; role lines match `-` slug`**[Role]** :` and use the seven link roles; every NOTE uses one of the six kinds (the retired `context` among them, until the audit), with exactly one slug where the kind takes one.

**Debt counters** (fail only if a count rises above its baseline), as of 2026-11-14: all nine at 0, including `minted_without_roster`. Every minted thread has a roster file, so a newly minted thread needs its roster file in the same commit. The last run (2026-11-23) checked 340 log entries (2 read with no thread) in 8 year files and 45 rosters, with 672 messages passing `validate_messages.py` and 24 prayer files passing `validate_prayers.py`.

When work clears items, the script prints the new baseline to set. To get a worklist for a category, set its baseline to 0 temporarily: the run lists the items with their files and line numbers. Restore the real count before committing.

The checks catch mechanical forms only. Ordinary-language stale claims ("the two purpose statements", "three are in hand", "the anchor is still awaited", "the thread lacks") and misquotes get past them, so the written rules above are the real protection. A pattern that flags good sentences was tried and reverted; precision matters more than coverage.
